## 0. 范围与前提

### 0.1 关键范围决策：M1b = 骨架通电（与文档原 M1b 的偏离）

宏观文档把 M1b 钉为「跑通 investigation 端到端」。**维护者 2026-06-15 拍板收窄**：下一步未必先做线上反馈排查，因此 M1b 降级为**纯骨架通电**，不绑任何业务 worktype——先证明「容器 + 真 agent + 飞书」三者能接通电。

**M1b 只做 4 样底座（与具体工作类型无关）：**

| # | 底座 | 为什么必须 |
|---|---|---|
| ① | workitems effect 接真 kernel runner（走 WI-C 并发槽） | 现在 effect 跑 noop run-handler，不换真 runner 工作项永远只能跑假的——最根本的接缝 |
| ② | 飞书入口命令 → 建 workitem → 建 thread → `claimThread('managed')` → 锚点卡片 | 没有它工作项无法从飞书创建、无法被人看到；WI-D 注册表的第一个真正使用方 |
| ③ | 人工介入通道 + 路由共存 | thread 里发消息进 agent 下一轮；工作项消息不被桥 task fallback 吞（用 WI-D） |
| ④ | 一个极简占位 worktype | 「单 agent、只读、跑一轮看代码、产出 report.md」= noop 在真 agent 上的等价物，验证骨架真的通电 |

合起来 = **一个工作项能从飞书创建 → 跑一个真 Claude → 产出报告 → 回飞书 → 人能在 thread 里追问 → 满意后关闭**。

### 0.2 已定技术决策（维护者授权 Claude 主导，已固化）

- **runner = Claude，权限 = readonly 弱档**（M1a WI-B 已做的那档）。强只读（Codex sandbox 禁网）随业务 worktype 一起推迟——它存在的唯一理由是「带真生产凭证防 curl 外传」，占位 worktype 只读看本地代码、不碰任何凭证，弱档威胁面在此不成立。
- **effect→runner 接缝走方案 A：managed 影子 task 行**（见 §2）。为每个 assignment 在 kernel `tasks` 表 upsert 一条 `owner_kind='managed'` 的 task，run handler 经装配注入的 `pool` 调**现有** `pool.send`；隔离靠桥侧所有 task 出口加 `owner_kind='bridge'` 过滤，与 WI-D 的 `thread_claims.owner_kind` 完全同源。否决方案 B（kernel `runSession` 原语 + runner 状态回写重构），留 M3 多 Worker 并行时再说。
- **多轮模型（v2 核心）**：probe 跑一轮后**静默 idle（非终态）**，等追问或显式关闭。每一轮（首轮 / 追问 / 重派）都是**一个独立的全新 assignment + 全新影子 task + 全新 Claude 会话**，上下文经 prompt 重建（前一份 report + 批量 human_message），符合 §5.3「Worker 无状态、用完即弃」与 P2「artifact 优先于记忆」。
- **占位 worktype 暂名 `probe`，创建命令 `/probe`，关闭命令暂名 `/done`**（命名是交互细节，可改；见 §6 D7）。

### 0.3 明确不做（防范围蔓延）

- ❌ integrations 适配器（日志/Sentry）、凭证 deny 列表——移交下一里程碑
- ❌ knowledge 知识层（repo map / _system / 选择性注入）——移交下一里程碑
- ❌ Codex 强只读（`--sandbox read-only`）——随业务 worktype + 真凭证一起做
- ❌ 卡片按钮回调原语（M2）——锚点卡片是纯展示，用现有 `sender.sendCard/replyCard`
- ❌ **§6.5 的重量级 `/cancel` 收尾序列**（确认卡 + abort 所有 assignment + 回收 worktree + Owner 收尾 journal）——M1b 只做**最小 `/done`**：注入终态事件，resting probe 无在跑 assignment 即干净终态；关闭时若恰有 run 在跑，`finalizeTerminalState`（reducer.ts:336-341）**即刻把该 assignment 标 superseded**，但底层 runner **不被 SIGINT**、跑完即弃、其 `run_completed` 经终态短路丢弃，期间仍占一个 WI-C 并发槽（验收若查 assignment 状态会见 superseded，预期对齐）。主动中断留 §6.5。

- ❌ 多 Worker 拓扑 / worktree（M3）；占位 worktype 是 solo
- ❌ 同一 assignment 的真 `--resume` 中途续接——M1b `canResume=false`，崩溃即作废重派（§2.3）

  - **run handler / probe worktype 落在 `src/worktypes/`（业务顶层，非 kernel），可自由使用 `assignment` 等词**；它 import kernel（`AgentPool`/`Store`）合法——依赖方向 `worktypes → kernel`。

**M1 评审 · 诚实的隔离边界**：方案 A 的隔离覆盖「面向用户的 task 查询出口」（上表 5 处，加 `owner_kind='bridge'` 过滤）。但真 runner 仍会对影子 task 写两类 kernel 副作用，**M1b 接受、写明以免验收时自我怀疑**：
- `store.logEvent(taskId, 'tool_start'/'done', ...)`（`claude/runner.ts` handleEvent）→ 工作项 agent 的 tool 活动混进 kernel `events` 表。**无面向用户的查询出口**（`recentEvents` 仅按 id 内部用，无命令暴露；FK `ON DELETE CASCADE` 随影子 task GC 一并清）→ 接受。
- `store.setStatus(taskId, 'hot'/'suspended')`（runner 生命周期）→ 写影子 task 的 status 列。**但 `/status`（桥）的 hot/suspended 计数走 `listTasks`，已被 `owner_kind='bridge'` 过滤掉影子 task** → 不污染计数。
- 结论：「对桥不可见」精确表述为「**对桥的路由/卡片/list/rm/status 计数不可见**」；events 表的运行副作用无用户出口，是边界不是 bug。

> 设计立场（§9.2）：managed 影子 task 是 kernel 运行原语被 workitems **借用**，对桥的面向用户出口不可见。隔离 = 所有面向「用户桥任务」的查询加 `owner_kind='bridge'`；面向「按 id 精确定位运行通道」的内部查询（runner 回写）不加过滤（D6）。

## 2. 核心接缝：effect → 真 runner（方案 A）

### 2.1 影子 task 的生命周期与 session 权威（v2 已纠正）

**身份（D4）**：影子 task 的 `id` 由 **assignment id** 确定性派生（`managed:<assignmentId>`）。**每个 assignment 一条独立影子 task 行**——不跨轮复用。多轮追问 = 多个 assignment = 多条影子 task 行（旧行随被替代的 assignment 留存，GC 列 §7）。

**字段来源**：

| Task 字段 | 来源 |
|---|---|
| `id` | `managed:<assignmentId>`（确定性，per-assignment） |
| `owner_kind` | `'managed'`（**新增列**，默认 `'bridge'`） |
| `agent_kind` | `'claude'`（Claude-first；未来可由 workitem.context 指定） |
| `cwd` | `workitem.repos[0]`，缺省回落 `cfg.probeDefaultCwd`（新增容器配置，默认 = kernel `allowedCwdPrefixes[0]` 或 DATA_DIR 下沙箱目录）；run handler 建 task 前 `mkdirSync(cwd,{recursive:true})` |
| `model` | `null`（用 Claude 默认 model） |
| `agent_session_id` | **首建即 `null`**（新 assignment 不继承旧会话）；turn 中 runner 写入工作副本（见下「session 权威」） |
| `mode` / `display_name` / `status` | `'project'` / workitem.title 截断 / `'suspended'` |

**session 双写权威（M2 评审）**：两份 `agent_session_id` 各有其位，实现者须分清：
- **kernel 影子 task.agent_session_id = runner 的每轮工作副本**。runner 在 turn 中 `handleEvent` 的 `case 'session'` 即 `store.setAgentSessionId(taskId, …)`（`claude/runner.ts:327-329`，另 close 时 :302 兜底）。它只在「该 assignment 的同一 turn 崩溃恢复」时有意义。
- **workitems assignment.agentSessionId = workitems 侧权威**，由 run handler 在 `pool.send` 返回后 `ctx.setAgentSessionId(result.sessionId)` 写入（effects.ts:274）。**M1b 仅作审计**（记录哪个会话产出了 report），不作 resume 锚点（`canResume=false`，§2.3）。
- **跨轮无需一致**：每个新 assignment 的影子 task `agent_session_id` 从 `null` 起，全新会话。两份只在「单 assignment 生命周期内」短暂并存，不存在「该信哪份」的跨轮冲突。

**生命周期**：run handler 在 `run(ctx)` 开头 `kernelStore.upsertTask({… owner_kind:'managed', agent_session_id:null})`。turn 结束影子 task 行**不删**（留作审计 + 崩溃恢复窗口）；工作项终态时不强制清理（GC 列 §7）。

### 2.2 通用 run handler 的控制流（`pool.send` ↔ `EffectContext` 映射）

run handler **不是 probe 专属**——它是「任意 solo 只读 worktype 的真 agent 运行器」，未来 investigation/bugfix 可复用（D5）。worktype 的 `onEvent` 只决定**何时派一轮 solo run**；run handler 自包含地组装 prompt（不依赖 `spec.brief`，因为 wake_pending 重派走的是无 brief 的 `defaultDispatchSpec`，§2.4）。

```text
createAgentRunHandler({ pool, kernelStore, cfg, logger }) → EffectHandler { kind:'run', recovery:'resume-or-redispatch' }

run(ctx):                                    # ctx: EffectContext（effects.ts:16）
  asg = ctx.assignment                       # 必有；缺则 throw（同 noop:25）
  workitem = ctx.workitem
  # 1) prompt 自包含组装：原始诉求 + 前一轮 report（续上下文）+ 本轮批量追问
  batch = ctx.eventsSince(ctx.batchFromSeq)                 # 半开窗口含上一轮 run_completed（ADR-6）
  priorReportPath = lastRunCompleted(batch)?.payload.reportPath   # 见下注；run_failed 无 reportPath → undefined
  priorReport = priorReportPath ? ctx.readArtifact(priorReportPath) : undefined   # WI-2 新增 readArtifact
  followups = batch.filter(e => e.kind === 'human_message') # 上一轮后 thread 里的追问
  prompt = composeProbePrompt(workitem.title, priorReport, followups)   # 全文进 prompt，靠 artifact/消息重建上下文（P2）
  ctx.writeArtifact(`assignments/${asg.id}/brief.md`, prompt, 'probe brief')   # 审计留痕
  # 2) 影子 task upsert（§2.1，每 assignment 新行、session=null）
  task = kernelStore.upsertTask(shadowTaskFor(asg, workitem, cfg))
  # 3) 心跳桥接：runner onText/onToolUse → 容器 watchdog 心跳
  callbacks = { onText: () => ctx.heartbeat(), onToolUse: () => ctx.heartbeat() }
  # 4) 权限映射：worktype.permissions.mode='readonly' → RunOptions（§2.3）
  options = { permission: { mode: 'readonly' } }
  # 5) 中止桥接：容器 abort → SIGINT runner
  ctx.signal.addEventListener('abort', () => pool.abort(task.id), { once:true })
  # 6) 跑真 agent（全新会话，无 --resume；天然过 WI-C 并发槽）
  result = await pool.send(task, prompt, callbacks, options)
  if (ctx.signal.aborted) return                            # 被中止：不写结论，effects.ts 收口
  if (result.error) throw new Error(result.error)           # → effects.ts emit run_failed
  # 7) 产出：agent 全文 → report.md（validateRunReport 门校验非空 → run_completed）
  ctx.setAgentSessionId(result.sessionId)                   # 审计：记录产出会话（M1b 不作 resume 锚点）
  ctx.writeArtifact(`assignments/${asg.id}/report.md`, result.fullText, 'probe report')

canResume(): false                            # M1b：无 onSession 回调，session 不可靠中途落 assignment → 崩溃即作废重派（§2.3）
resume = run                                  # 形式保留（recovery 走 redispatch，不会真调 resume）
```

> `lastRunCompleted(batch)`（续上下文取数，评审 2 写死）：`EffectContext` **不暴露 `listAssignments`**，且每轮 assignment id 不同，**不能**靠枚举 assignment 找上一份 report。正解：`run_completed` 事件的 payload 带 `reportPath`（`effects.ts:212/327` emitRunConclusion 第 4 参），而 `ctx.eventsSince(batchFromSeq)` 的半开窗口（ADR-6，`batchFromSeq = lastRunEffectSeqBefore`）**恰好包含上一轮的 `run_completed`**。故 `lastRunCompleted` = 「批量里 seq 最大的 `run_completed`」，取其 `payload.reportPath`。天然正确处理「上一轮失败」（只有 `run_failed`、无 reportPath → `priorReport=undefined`）。

**与现有机制的契合点**（为什么改动小）：
- `pool.send` 返回后 run handler **正常返回** → `effects.ts:209-215` `validateRunReport` 检查 report.md 非空 → `emitRunConclusion('run_completed')`。报告缺失/空 → `run_failed`。**义务校验（§4.4）零改**。
- run handler 抛错 / `result.error` → `effects.ts:222` `emitRunConclusion('run_failed', err)` → worktype onEvent 决定重派或终态。
- 并发：`pool.send` 内部 `slots.acquire`（`pool.ts:134`）→ 工作项的真 agent 运行自动受全局并发上限约束，**与桥消息共用一个池**。

### 2.3 心跳 / 中止 / 恢复 / 权限 四条桥接

- **心跳**：`callbacks.onText → ctx.heartbeat()`。这让 M0 设计的 watchdog（心跳静默 / 墙钟 / 死线 → `assignment_stalled`）对**真 agent** 生效——M0 时只有 noop 自打心跳，M1b 第一次接到真流式。
- **中止**：`ctx.signal`（来自 `EffectRuntime.abort`，effects.ts:133）→ `pool.abort(task.id)`（pool.ts:174 → runner SIGINT）。容器侧 stalled/关闭 能真正打断在跑的 Claude。
- **恢复（v2 纠正）**：M1b **`canResume=false`**。原因：run handler 拿不到 turn 中途的 sessionId（`ProgressCallbacks` 无 onSession 回调，§1.2），`assignment.agentSessionId` 要到 `pool.send` 返回后才写——崩溃窗口内它仍是 `null`。故 `effects.ts:91-122` recoverRun 判 `canResume=false` → **作废重派新 assignment**（replaces 链、全新会话）。只读 probe 重跑幂等（重新读代码），无副作用。**真 `--resume` 中途续接 = 未来增量**（加 onSession 回调把 session 即时落 assignment，§7）。
- **权限**：worktype 层 `PermissionProfile{readonly|write}`（`workitems/types.ts:88`）≠ agents 层 `PermissionProfile{full|readonly}`（`agents/types.ts`）。映射在 run handler：`readonly → {mode:'readonly'}`；`write` M1b 不出现。**两个同名类型的语义差是刻意的**——worktype 声明意图，agents 层 enforce 手段。

### 2.4 多轮追问的两条路径（v2 新增，复用 M0 单飞机制）

probe **跑一轮后静默 idle（非终态）**，等追问或关闭。追问（`human_message`）有两条进入路径，**都不需新增并发原语**：

- **路径 A · idle 时追问**（无在跑 run）：`human_message` apply → `probe.onEvent` 返回 `{dispatch:[solo run]}` → `insertDispatchOrWake` 无在飞效果 → 建新 assignment + run 效果 → poke → 跑。
- **路径 B · run 进行中追问**（单飞）：`human_message` apply → `probe.onEvent` 返回 dispatch，但 `insertDispatchOrWake`（reducer.ts:585-592）见 `hasInflightRunEffect` → 置 `wake_pending`、不建第二 assignment。当前 run `run_completed` apply（reducer.ts:215-217）→ `releaseWakePending`（:627-631）→ **`insertDispatchOrWake(defaultDispatchSpec)`**（容器默认 solo run，无 brief）→ 新 run，批量追问经 `ctx.eventsSince` 带入。

> 关键：路径 B 的重派用**容器 `defaultDispatchSpec`**（无 worktype brief），这正是 §2.2 run handler **不依赖 `spec.brief`、自包含组装 prompt** 的原因——两条路径产出等价的 solo run，run handler 统一从 `workitem + 批量事件 + 前一份 report` 重建上下文。

## 5. 验收（M1b Done 的定义）

1. **端到端真活 + 多轮**：飞书 `/probe <描述>` → 锚点卡 → 真 Claude 跑一轮（只读）→ report.md → 回贴 thread → **thread 内追问能进下一轮 agent 上下文且带上前一轮 report** → `/done` 关闭到 done 终态。（飞书手验 + 集成测）
2. **effect 走真 runner**：生产装配的 run handler 是 `createAgentRunHandler`，noop 仅存于测试夹具；工作项运行经 `pool.send` 过 WI-C 并发槽（`/diag-slots` 能观察到 managed 运行占槽）。
3. **路由共存零串台**：managed 影子 task 不出现在 `/list`、不可被 `/rm`、不被 fallback 浮出、不污染 `/status` 计数；未认领 thread 的桥行为与 M1b 前逐字节一致（单测钉死）。
4. **watchdog 对真 agent 生效**：心跳静默 / 墙钟超限能产生 `assignment_stalled` 并 SIGINT 真 runner（注入超墙钟 probe 验证）。
5. **崩溃恢复**：运行中 SIGKILL → 重启 `recoverRun` 判 `canResume=false` → 作废重派新 assignment（全新会话重跑，只读幂等）；集成测验证不双跑、不卡死。
6. **idle 非终态正确性**：`run_completed` 后工作项停在 `active`（idle）、watchdog 不误触 stalled；`/done` 后到 `done`（单测 + 集成测钉死 S1 修正）。
7. `npm run check` 全绿；`tests/architecture.test.ts` 守门通过；M0 全套回归零退（基线取执行时 `npm run check` 实跑数，HEAD 已含 M1a）。
8. 决策台账（§6）已与维护者确认。
