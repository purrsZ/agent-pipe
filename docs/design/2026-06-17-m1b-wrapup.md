## 0. 背景：M1b 通电后还差「最后一公里」

WI-6 把**成功路径**的 report 回贴打通了，但 WI-6 文档 §3 明确把两件事划到边界外、§5 移交本步：

1. **失败不回贴**：`onReport` 是 run handler 的直接回调，**只在成功路径调**（abort 早返回、失败抛错都不到）。用户 `/probe` 后若 Claude 跑失败或重试耗尽，**飞书侧锚点卡一动不动**，用户干等。
2. **锚点卡不随轮刷新**：锚点卡只在创建（`/probe`）和关闭（`/done`）时更新。中间 `looking → idle → looking → idle` 的进度、失败 `failed`，飞书侧都看不到。

WI-6 §5 给了方向：**「随方案 2（容器结论事件订阅出口）一起做；届时可统一 `run_completed`/`run_failed` → 回贴 / 更新锚点卡」**。本文落实方案 2。

> 第三件收尾事——**飞书端到端手验**——是真 bot + 真 Claude 才能跑的人工验证，代码无法替代。清单见 §5，与本步代码并行。

## 1. 决策：方案 2（容器结论事件订阅出口）

WI-6 当时**否决**方案 2、选 run handler 回调，理由是「不想为单一订阅方扩容器表面（单向门）」。现在订阅方增加到**三类**（成功回贴 / 失败回贴 / 锚点卡刷新），run handler 单点回调不够用——**方案 2 的时机到了**，这正是 WI-6 §1 表格里「留待真有多订阅方时再做」的那一刻。

**最小扩面论证**：容器**已有**提交后出口——`ReducerRuntime` 的 `postCommit(actions)`（reducer.ts:226-228，container.ts:55）在每次 `applyEvent` 事务**提交后**触发，是做异步 IO（回贴飞书）的正确时机（事务外、状态已落地）。方案 2 **不新建订阅总线**，只在这个已有钩子旁加一个**事件观察者出口** `onCommitted(workitemId, event)`，把刚提交的主事件透传出去。扩面 = reducer 多一个可选 dep + container 多一个透传参数。

| 子决策 | 选择 | 理由 |
|---|---|---|
| D1 挂载点 | reducer 新增可选 dep `onCommitted?(workitemId, event)`，在 `applyEvent` **事务提交后**、与 `postCommit` 同段触发 | 复用已验证的「提交后」时机（IO 必在事务外）；不污染 `postCommit` 的「容器内部动作」语义 |
| D2 通知内容 | 只传**触发本次 apply 的主事件**（reducer.ts:198 的 `event`），不传 phase_changed 等审计事件 | index 侧自己 `getWorkItem` 读最新投影刷锚点卡，reducer 零额外收集 |
| D3 成功回贴归属 | **保留 WI-6 的 `onReport`** 专做「成功 report 全文回贴」（它直接握有 `result.fullText`）；observer 只补**失败错误卡** + **锚点卡刷新** | 职责清晰、改动最小；observer 读不到 report 全文（只在 artifact） |
| D4 失败回贴粒度 | **仅终态 `failed`** 回错误卡 + 刷失败锚点；中间 `run_failed`（还要重试）走「非终态」分支只刷 stage | 避免重试噪音刷屏；终态才是用户要知道的「这事黄了」 |
| D5 锚点卡刷新 | **非终态**推进后 observer 反查 thread root → `updateCard(buildAnchorCard(item 最新))` | 锚点卡变「活」：looking/idle 实时可见 |
| **D6 终态锚点归属（评审补）** | **`done`（close_requested 触发）→ observer 不碰锚点**（`runDone` 已 `updateCard(closed:true)`）；**`failed`（run_failed 触发）→ observer 全权**：错误卡 + 刷失败锚点 | `/done` 同步触发 `onCommitted` → 才 `await updateCard`；若 observer 也刷 done 锚点会与 runDone 抢同一消息、顺序由 HTTP 定（两卡 `closed` 不同**不幂等**，可能停在蓝卡）。done 归 runDone、failed 归 observer，各有唯一负责人 |
| **D7 决策抽纯函数（评审补）** | 抽 `anchorAction(kind: string, isTerminal: boolean): { reply: boolean; update: boolean }` 纯函数；index 用 `isTerminalStatus(item.status)`（shared.ts:27）判终态，**不写 `status===`** | 既单测覆盖三分支、又绕开 index-wiring 行 49 的 `status\s*={2,3}` 守门；纯函数吃原始 bool、零依赖业务类型，落 `feishu/` 层可安全单测 |
| **D8 failed 终态收尾（评审 P1）** | `failed`（被动终态、无 `/done` 入口）→ **claim 不自动释放**（保留使 footer「可 /done」有效、`/done` 仍能收尾）；dispatcher 的 managed 分支加**终态守卫**：终态项 → 诚实回执（「该调查已结束，回复 `/done` 关闭后可重新 `/probe`」）而非 `injectHumanMessage` + 「已转交…稍候」 | 否则 failed 后 thread 追问命中悬挂 claim → `injectHumanMessage` 进终态短路（reducer.ts:153）只记事件不 dispatch → 报告永不来 + 误导回执（复活 §0 要消灭的「干等」，只是换触发点）。这也堵住**既有缺陷**（任何终态 + 残留 claim）。否决 (a) 自动释放 claim：footer 失效 + 追问回落 bridge 误落无关任务 |

## 2. 设计

### 2.1 数据流

```
reducer.applyEvent(workitemId, event):
  let committed                                    # tx 外声明：reducer.ts:198 的 event 在 tx 闭包内（评审 #7）
  tx { ... apply ... recomputeRollup; committed = event }
       # 终态短路(:153) / conclusion_rejected(:168) / decision_discarded(:184) 三条 early-return 不赋值 → 不触发 onCommitted（对：已终态/被拒/被弃本就不该刷卡）
  postCommit(actions)                              # 已有：abort/poke
  if (committed) onCommitted(workitemId, committed)   ◄── 新增：事务后透传主事件

index.ts 装配 onCommitted 闭包 postStatus(workitemId, event)：
  item = workitems.api.getWorkItem(workitemId)
  const { reply, update } = anchorAction(event.kind, isTerminalStatus(item.status))   # D7 纯函数 + shared.ts:27（绕开 status===）
  threadRoot = getThreadRootByOwner(workitemId)        # = claim 的 anchorMsgId（P3：reply/update 同一个值，勿反查两个 id）
  reply  → threadRoot ? replyCard(threadRoot, buildErrorCard(item.title, errorFromPayload(event)))
                      : sendCard(chatIdFromSource(item.source), …)   # 回落 chatId，同 postReport（P2）
  update → threadRoot ? updateCard(threadRoot, buildAnchorCard(item 最新，含 failed 视觉态))
                      : log（updateCard 需原消息 id，无 threadRoot 无法回落 → 放弃 + log，P2）
  # 成功 report 全文回贴仍由 WI-6 的 onReport/postReport 负责，不变（D3）

anchorAction(kind, isTerminal)：
  run_failed && isTerminal → { reply:true,  update:true  }   # 错误卡 + 失败锚点（failed 归 observer，D6）
  isTerminal（即 done）     → { reply:false, update:false }   # 跳过，归 runDone（D6）
  否则（非终态）            → { reply:false, update:true  }   # 刷 stage
```

锚点刷新与 report 回贴的区别：**刷新 = `updateCard` 改原锚点消息**；**report 回贴 = `replyCard` 在 thread 下发新报告卡**。两者并存不冲突。

> **bootstrapApply 不触发 onCommitted（评审 #3）**：`workitem_created` 走 `bootstrapApply`（reducer.ts:79-136，独立事务、不经 applyEvent、无 postCommit），**首卡不靠 observer**——`runProbe` 建锚点卡时 `item.phase` 已是 `probe:looking`（createWorkItem 同步跑完 bootstrap），天生正确。observer 只覆盖「create 之后」的推进，**不为 onCommitted 去额外挂 bootstrapApply**（徒增面）。

> 终态锚点的唯一负责人见 **D6**：`done` 归 `runDone`（即时反馈用户操作）、`failed` 归 observer。两者不再「重复幂等」——是**不**幂等（卡渲染不同），故按负责人切开而非「择一」。

### 2.3 守门注意

- `reducer.ts` / `container.ts` 用中性词（`onCommitted` / `event`），不触发 kernel 业务词守门。
- `buildErrorCard` 用 `title` / `error`，不出现禁词。
- `index.ts` 的 `postStatus` 闭包**与 dispatcher 终态守卫（改动点 5）**都避开 `workitems.*status/phase` 同行与 `status==`/`phase==`（index-wiring.test.ts 行 49 正则）：`workitems.api.getWorkItem(...)` 与读 `item.status` **分两行**（正则第一段 `workitems?\.[^\n]*(status|phase)` 会咬同行写法，评审 Minor）；终态判定一律走 `isTerminalStatus(item.status)`。

## 3. 边界（明确不做）

- ❌ **report 流式回贴 / 锚点卡按钮**：仍是 M2（卡片回调原语）的事，本步只更新卡内容、不加交互。
- ❌ **每个 phase_changed 都单独通知**：observer 只收主事件，phase 细节由 index 读最新投影，不做逐 phase 事件订阅。
- ❌ **把 WI-6 的 `onReport` 并入 observer**：成功回贴维持现状（D3），避免无收益的重构。
- ❌ 主动中断 / 重量级 `/cancel`（§6.5）：仍属未来。

### 3.1 已知边界（接受，评审 Minor）

- **冗余刷新**：observer 对所有非终态主事件（含 `effect_aborted`/`assignment_stalled` 等容器审计事件）都 `updateCard`，部分内容未变即冗余刷。当前无害（`updateCard` 幂等）；在意飞书 API 频率时给 `anchorAction` 加事件白名单（只对会改投影的主事件 `update`）。
- **anchorAction 的 done 假设**：第二分支「`isTerminal` 即 done」隐含「非 `run_failed` 的终态都归 runDone」。probe 当前只有 done/failed 两终态、成立；**未来新增终态（如 cancelled）需重审**此分支。

## 4. 验收

> 测试分层（评审 #8）：`postStatus → sender` 的**实参**是 index 层、`probe-e2e`（容器层 + fake pool、无 sender）够不着——故核心逻辑下沉到 `anchorAction` 纯函数单测，容器测只断言 `onCommitted` 序列，sender 实参走 index-wiring grep + 手验（与 WI-6 对 `postReport` 同款处理）。

1. **anchorAction 纯函数单测（核心）**：`run_failed`+terminal → `{reply:true,update:true}`；terminal（done）→ `{reply:false,update:false}`；非终态 → `{reply:false,update:true}`。
2. **onCommitted 时机 + 短路（单测）**：事务**提交后**触发；终态短路 / conclusion_rejected / decision_discarded 三条 early-return **不**触发。
3. **失败回贴 + failed 后追问（probe-e2e + 单测，评审 P4/P1）**：① fake pool **连续失败 maxRetries+1=2 轮**（probe `maxRetries` 默认 1，**非** harness 的 `WORKITEMS_RETRY_BUDGET`——后者是 reducer stall 路径、对 `run_failed` 无效）→ 终态 `failed` → `onCommitted(run_failed)` 序列被断言；② 终态项的 thread 追问 → dispatcher 走诚实回执、**不** `injectHumanMessage`（单测 dispatcher 守卫或手验）。
4. **卡片渲染（单测）**：`buildAnchorCard({status:'failed'})` 出红 header + 「已失败」footer；`buildErrorCard` 渲染 title + error 摘要 + 超长截断。
5. **成功回贴不回归**：WI-6 的 `onReport`/`postReport` 行为逐字节不变。
6. **装配接线（index-wiring grep）**：`postStatus` 接 `updateCard`/`replyCard`、用 `isTerminalStatus`（**无 `status===`**）；`sender` Pick 含 `updateCard`。
7. **不验** `workitem_created → onCommitted`（评审 #3：走 bootstrapApply，本就不触发；首卡由 runProbe 保证正确）。
8. `npm run check` 全绿；架构 + index-wiring 守门通过；M1b 既有 279 测试零退。

## 5. 飞书端到端手验清单（维护者在真 bot + 真 Claude 环境跑）

> 这是 M1b 验收 §5.1 / WI-6 §4.1-4.2 的人工部分，代码替代不了。本步代码合入后一并验。

1. **成功闭环**：`/probe 看看 src 里有几个 runner` → 收到蓝色锚点卡（id/进度/状态）→ 数十秒后 thread 下收到绿色**报告卡**（report 全文）→ 锚点卡进度刷新为 `idle`。
2. **多轮追问**：在锚点卡下回复一句追问 → 第二轮跑完 → 新报告卡回贴 thread，且内容延续上一轮（带前文）。
3. **失败回贴 + 失败锚点**（本步新增）：构造会失败的诉求（如指向不存在的目录 `/probe --repo /nope 看看`）→ 重试耗尽 → 终态 `failed` → 收到红色**错误卡**，且**锚点卡刷成失败态**（红 header「调查失败 · …」、footer「已失败，可 `/done` 关闭」）。中间重试轮不刷屏（仅终态回卡，D4）。
4. **failed 后追问 + 收尾**（本步新增，评审 P1）：上一步 `failed` 后在 thread 追问 → 收到「该调查已结束，`/done` 后可重新 `/probe`」诚实回执（**不**假装受理）→ `/done` 仍能把锚点卡收为「已关闭」、释放 claim。
5. **关闭**：`/done` → 锚点卡变灰「已关闭」→ 同 thread 再追问，回落正常桥路由（不再被 managed 认领吞）。
6. **并行上限**：连开 4 个 `/probe`（不 `/done`）→ 第 4 个收到「已达并行上限（maxOpen=3）」友好提示，不崩。
7. **并发占槽**：两个 probe 同时在跑时 `/diag-slots` 能看到 managed 运行占用 WI-C 并发槽。

## 6. 依赖顺序与工作量

```
WI-7a（reducer.onCommitted 出口 + container 透传）──┐
WI-7b（card：buildErrorCard + buildAnchorCard failed 态 + anchorAction 纯函数 + 单测）──┼─► WI-7c（index 装配 postStatus：isTerminalStatus + anchorAction 分发 + sender 加 updateCard）
                                                     │                                    │
                                                     │              probe-e2e 扩失败回贴（onCommitted 序列）断言
```

- 体量：~1 个 commit 量级（reducer/container/index【装配段 + **dispatcher 段**，P1】/card 四文件 + anchorAction 单测 + probe-e2e 扩 `onCommitted` 收集器），仍远小于 WI-2~6。
- **anchorAction 纯函数承载全部分支逻辑**（D7），是验收 1 的单测靶子，也让 index 侧免写 `status===`。
- **P1 修的是既有缺陷**（终态 + 残留 claim 吞追问），WI-7 让 `failed` 可达后它从「被 done 规避」变「必触发」，故并入本步。
- 与 §5 手验并行：代码合入即可手验。
