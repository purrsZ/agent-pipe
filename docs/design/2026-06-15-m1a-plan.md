## 0. 范围与前提

M0 把 workitems 容器语义在内存里用 noop 打穿，没碰飞书、没碰真 agent、没碰权限。
M1a 转向 **kernel 层**，补四项「通用能力」。准入标准（P1）：**对一个纯飞书桥用户也有意义** →
进 kernel，不进 worktypes。验收标准：**四项各自独立可验**，不依赖 investigation 类型跑通。

### 0.1 关键范围决策：Claude-first（与文档原假设的偏离）

文档把「只读权限档」在 M1a 钉死为**仅 Codex**，理由是安全：Codex 的 `--sandbox read-only`
是 OS 级沙箱、默认禁网；Claude 只能配置级 deny（弱），拦不住 `curl` 外传。

**现实**：本项目当前只用 Claude，后续才会引入 Codex。严格「只做 Codex」会让只读档现在无法验证。
因此 M1a 调整为：

- **主体 = 三项 runner 无关 / 弱相关能力**（工具注入、最小排队、thread 路由）：Claude 现在即可用、可验。
- **权限档 = 只做接口骨架 + Claude `readonly` 弱档**（配置级 deny，**明确标注「非强隔离、不禁网」**），
  不拿它跑带敏感凭证的活。
- **强只读（OS 沙箱禁网，仅 Codex）= 登记为 M1b 前置依赖**：在 M1b 用真实日志 / Sentry 凭证
  跑 investigation 之前，必须先接入 Codex 只读档。详见 §6 决策台账。

### 0.2 验证形态

每项能力 = **单测 + 一个临时桥调试命令**（`/diag-*` 前缀，M1b 收编或移除）。
理由：文档要求「桥用户可独立感知验证」，而本项目的桥用户用 Claude。

**`/diag-*` 命令的两条硬约束**：
- **🔒 一律 admin-only**（review #3）：`/diag-mcp` 让用户指定 MCP server 的 command/args ＝ 任意命令
  执行入口；`/diag-claim`、`/diag-readonly` 改路由/权限。全部 gate 在 `CommandHandler.isAdmin`
  （`commands.ts:54`）之后，非 admin 直接拒绝。
- **🚫 落点不得触发守门禁词**（review #1）：`bridge/commands.ts` 是 kernel 层（`architecture.ts:112`
  只豁免 `index.ts`/`config.ts`），diag 命令的参数解析里**不得出现 `workitem`/`assignment`/`phase`
  等字面量**——认领参数统一用 `managed|bridge`；涉 workitems 语义的分支放 `index.ts`（豁免层）。

### 0.3 明确不做（防范围蔓延）

- ❌ 命令命名空间分离 / 共存路由的 workitems 端（M1b）
- ❌ 把 workitems 的 effect 接到真 runner（M1b：effect 现在仍是 noop run-handler）
- ❌ 调度优先级 / Owner 预留槽 / worktree 并行（M3）
- ❌ Claude 写权限档与强只读重做（M2）
- ❌ knowledge / integrations 适配器（M1b）

### 0.4 守门

- `tests/architecture.test.ts`：依赖方向严格单向，kernel 不出现业务概念词。
- `npm run check`（typecheck + biome + vitest）全绿。

## 2. 共同基建：RunOptions 管道（WI-A / WI-B 的地基）

工具注入与权限档都需要「每次 run 能带一组启动选项」。但有一条**硬约束决定了生效粒度**：

> **RunOptions 是 per-process 生效，不是 per-turn。** 两个 runner 的进程模型相反：
> - **Claude = long-lived proc**：`claude/runner.ts:89-91` 只在 cold/killed 时 `spawn()`，args
>   （含 `--dangerously-skip-permissions`、未来的 `--mcp-config`）在 spawn 那一刻一次性固定
>   （:148-163）；后续 `runTurn` 只把 prompt 写进已存在进程的 stdin（:112），**不重建**。
>   `pool.ts:53-66` 在 runner hot 时只 `setTask` 刷快照。→ 第一轮 spawn 定型，后续轮传不同
>   options **静默失效**（review S2）。
> - **Codex = per-turn spawn**：`codex/runner.ts:100+` 每轮重建 `finalArgs` 并 spawn，天然支持每轮换 options。
>
> ⚠️ **难度方向是反的**：per-run 选项在 per-turn 的 Codex 上几乎免费，在 long-lived 的 Claude 上
> 才需要额外机制。本计划先做 Claude（因为只用 Claude）、推迟 Codex，是被现实倒逼，**不是因为
> Claude 更容易**——执行时别被「先做的应该更简单」的直觉误导。

**机制定为「options 指纹变更 → 重建 runner」**（类比现有 `modelChangeRequiresRespawn`）：

- pool 记住每个 task 上次的 options 指纹（permission + mcpServers 的稳定序列化）。
- `send()` 里指纹变更的处理**对称复用现有 kind-changed 重建路径**（`pool.ts:43-51`）：
  **丢弃旧 runner 实例**（`dispose()` + `runners.delete`）→ `createRunner` 新实例。
  ⚠️ **不能在同一 runner 实例里 `dispose()` 旧 proc 再 spawn**（review #2）：`dispose()` 置
  `this.disposed=true`，而 close handler `claude/runner.ts:221 if(this.disposed) return` 会让新 proc
  退出时**不写 session/status**，埋状态不一致。新实例 `disposed=false`，从 `task.agent_session_id`
  读回 sessionId（constructor:63）→ `--resume` 自然恢复，上下文不丢。
- Codex 无需特殊处理（下一轮 spawn 自然带新 args）。
- 所有 `/diag-*` 验证命令对 **hot task 必须先触发重建**，否则验证假阳/假阴。

```ts
// agents/types.ts（新增）
export interface PermissionProfile { mode: 'full' | 'readonly'; }   // M1a 两档；'write' 留 M2
export interface McpServerSpec {
  name: string; command: string; args?: string[]; env?: Record<string, string>;
}
export interface RunOptions {
  permission?: PermissionProfile;       // 缺省 = full（保持现有行为，零回归）
  mcpServers?: McpServerSpec[];          // 缺省 = 不注入
}
export function runOptionsFingerprint(o?: RunOptions): string;     // 稳定序列化，供 respawn 判定
```

下传通道（方案 A）：`Runner.runTurn(text, callbacks, options?)` 加可选第三参；
`AgentPool.send(task, text, callbacks, options?)` 透传。桥 task 默认不传（= full、无注入、零回归）。
方案 B（扩展 `Task` 快照）要动 store schema，不选。

> 红线：缺省必须等价于当前行为（`full` + 无注入 + 不重建），桥任务零回归。

### 2.1 合并后的 `pool.send()` 控制流（WI-A + WI-C 的共同目标，防撞车）

WI-A（指纹重建）与 WI-C（并发槽）**改的是同一个 `pool.ts:39-72` 的 `send()`**（review R1）。
两者必须按下面这一份合并控制流落地，不可各写各的：

```text
send(task, text, callbacks, options, onQueued?):
  # 1) 纯读判定：是否丢弃现有 runner（kind 变 或 options 指纹变）
  existing = runners.get(task.id)
  if existing and (existing.kind != task.agent_kind or existing.fp != fingerprint(options)):
      existing.dispose(); runners.delete(task.id); existing = null   # ← acquire 之前，纯清理、不占槽
  # 2) 全局并发槽（WI-C）。满 → 先回一次 onQueued()，再 FIFO 等待
  if not tryAcquire(task.id):
      onQueued?.()                      # 把“因全局槽排队”信号交给豁免层（R2）
      await acquire(task.id)            # 抛出=取消：发生在 try 外、未占槽 → 不 release
  try:
      runner = existing
      if not runner:
          factory = factoryFor(task.agent_kind)   # 先解析，损坏 kind 不误伤热 runner
          if hotCount() >= maxHot: evictLRU()
          runner = factory.createRunner(task, deps, options); runners.set(task.id, runner)
      else:
          runner.setTask(task)          # 指纹未变才复用
      return await runner.runTurn(text, callbacks, options)
  finally:
      release(task.id)                  # 覆盖 runTurn 抛出/正常；步骤 1 的 dispose 不在 try 内
```

**不变量**：
- 步骤 1 的 `dispose()` 在 `acquire()` **之前**——该 task 接下来要重建，等槽期间不持进程是对的，
  且它不在 try 内、不参与 release 配对。
- `acquire()` 取消发生在 try 外 → 未占槽 → 不 release；**占槽成功后所有路径走 finally release**。
- 等槽空窗：步骤 1 已 dispose、步骤 3 还没 createRunner，中间隔着等槽——可接受（该 task 本就无活计）。
- **落地次序因此强制 A 先于 C**（C 在 A 已成形的 send() 上叠 acquire/release/onQueued），见 §4。

### WI-C：最小排队（全局并发槽）

- **意图**：给 kernel 引入「全局同时运行的 runner 数有上限，超了 FIFO 等待」，取代「忙时超 cap 硬 spawn」。
- **改动**：
  - `agents/pool.ts`：新增全局并发上限 `maxConcurrent`（≠ `maxHot`：maxHot=保持热的进程数，
    maxConcurrent=同时在 runTurn 的数量）。`acquire/release` + FIFO 等待队列**严格按 §2.1 合并控制流**
    （`acquire` 在 createRunner 之前，避免 evict 抖动/空占 maxHot，review M1）。
    **`send()` 新增 `onQueued?` 回调**：槽满需等待时回调一次，把「因全局槽排队」信号暴露给豁免层（review R2）。
  - **不变量 `maxConcurrent ≤ maxHot`（仅因当前只用 Claude）**：否则可有超过 maxHot 个 hot Claude
    runner 同时 runTurn，退回「忙时超 cap」。但这把两种资源模型耦合了（review #7）：maxHot 管的是
    **热进程内存**（仅 Claude 类常驻进程），maxConcurrent 管的是**并发压力**（全类）。Codex
    `isHot=false`、不占 maxHot，其并发本应只受 maxConcurrent、与 maxHot 解耦——Codex 接入时把这条
    不变量拆成「Claude 并发 ≤ maxHot」而非「全局 ≤ maxHot」。M1a 先按 ≤ maxHot 落地并注释清楚。
  - `config.ts`：新增 `MAX_CONCURRENT`（默认 = maxHot，可配，校验 ≤ maxHot）。
  - `index.ts`：把 `onQueued` 传给 `pool.send`，在回调里回「全局繁忙，已排队」——**现状 `:464`
    的排队反馈只在该 task 自己 busy 时触发，全局槽满但 task 不 busy 时会直接进 `runWithDrain:475`
    → `send` 内 `acquire` 阻塞、用户侧静默几十秒像掉线（review R2）**。
- **两层队列语义（正交，须在代码注释钉死）**：per-task 队列（`index.ts:464`，同一 task 多消息串行）
  解决「一个任务自己别并发」；pool 全局槽解决「跨任务同时跑几个」。一条消息先过 per-task 闸、
  再过全局槽。
- **接口/数据**：纯内存队列（与现有 per-task `queues` 同风格）；进程重启丢队列可接受（桥任务语义）。
- **验证**：
  - 单测：maxConcurrent=1 时第二个 `send` 在第一个 release 前不进入 runTurn（fake runner 计时断言 FIFO）；
    且**第二个 send 在拿到槽前不 createRunner**（断言 runner 未被提前建/evict）。
  - 临时命令：`/diag-slots` — 打印在跑 / 排队数。
- **边界**：**不做**优先级、不做 Owner 预留槽（M3）；不把 workitems effect 接进来（M1b）。
- **风险**：acquire/release 泄漏死锁 → release 放 `finally`，abort/dispose 路径也 release；
  加「槽计数 == 在跑 runner 数」不变量断言（dev 日志）。

    并 **return**（M1a 先打桩：记日志 + 友好回复占位，真正认领是 M1b）；否则走现有四层不变。
    > 注（review #4）：原写「后两层跳过 managed」是冗余——命中 managed 已 return，bridge 的
    > currentTask/mostRecent 是 task 中心、只会返回 bridge task，遇不到 managed thread。真正的反向
    > 串台（managed thread 消息未命中认领 → fallback 串到别的 bridge task）在 M1a 不可能发生
    > （还没有真 workitem），**连同其防护一并移交 M1b**。
- **接口/数据**：注册表只存 `thread → owner` 中性映射，不含任何业务字段或禁词（满足 P1 + 守门）。
- **验证**：
  - 单测：被 `managed` 认领的 root_id，路由不落到桥 task；未认领的 thread 行为与现状一致。
  - 临时命令：`/diag-claim <root_id> managed|bridge` 与 `/diag-unclaim <root_id>`（参数统一中性值，
    **不出现 `workitem` 字面量**）— 手动登记/释放认领，再发消息观察路由走向。
- **边界**：不实现 workitems 真正认领（M1b）；不动命令命名空间（M1b）。
- **风险**：现有四层 fallback 的回归 → 新增「未认领 thread 路由不变」单测把现状钉死。

## 4. 依赖顺序与并行性

```
WI-A（RunOptions 基建 + 工具注入）──► WI-B（权限档复用 RunOptions）
      │ 同改 pool.send()
      ▼
WI-C（最小排队：在 A 成形的 send() 上叠 acquire/release/onQueued）
WI-D（thread 路由）     独立
```

- **A → B**：B 复用 A 的 RunOptions 管道。
- **A → C（新增约束，review R1）**：A 与 C 改同一个 `pool.send()`，必须按 §2.1 合并控制流**串行**落地，
  不可并行两个 PR 撞同一函数；C 在 A 已成形的 send() 上叠 acquire/release/onQueued。
- **D** 独立，可任意穿插。
- 建议次序：**A → B → C → D**，或 A→C 串行、D 穿插、B 收尾。
- ⚠️ **WI-E 是条件触发的（review R3 / D6 / §7）**：**仅当** `/diag-readonly` 实测命中 ③（hang）才开——
  独立设计 turn wallclock 兜底（kernel 通用能力，对纯桥也有用）。**先实测再决定，不预先扩范围。**
