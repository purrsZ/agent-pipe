## 1. 背景与根因（只需读懂，不需复查）

真机现象：长回合期间飞书流式卡的**内容和时间同时冻住**（如定格在 `1:30 · 1 tools · 处理中…`），
agent 实际还在正常干活，几分钟后卡片"突然"变成完成态。2026-07-09 09:18 的 reopen 任务是标准案例：
09:18:08 开跑、09:23:50 仍在跑，期间**日志里零条 updateCard 失败**——请求既没成功也没报错，是挂起。

三层叠加：

1. **网络层（根因）**：bot 进程环境带 `HTTP_PROXY/HTTPS_PROXY=http://127.0.0.1:7897`（Clash），
   飞书 API 被迫走本机代理；代理抖动时请求**挂起不返回**（无 RST、无响应）。
2. **SDK 层（放大器）**：Lark SDK 用 axios，默认 `timeout=0` = 永不超时，挂起请求吊到 TCP 层
   自己断（分钟级）。
3. **StreamingCard 层（冻结直接原因）**：`src/feishu/stream-card.ts` 单飞行串行设计——`active`
   持有在途 PATCH，后续帧只置 `dirty` 排队。一个挂起请求堵死整条链：内容、5s 时间心跳、
   V3 stale 标注全部走这条链，一起冻住。

对照系统 `~/alaeat/ai-sentinel`（我们 StreamingCard 注释自述"mirrors ai-sentinel's, trimmed"）：
原版 `StreamUpdateController`（local-server/src/ai_sentinel/streaming/controller.py）有**单帧 3s 超时、
连续失败熔断 30s、在飞请求 shutdown 交接、结构化日志**，裁剪时全部丢了——本方案就是把这几件套
按我们的代码形态补回来，另加两刀底座（SDK 超时 + 飞书直连）。

## 3. 逐文件规格

### 3.1 `src/feishu/client.ts`

在文件内新增**导出**纯函数（供测试），并在 `createFeishuClients` 开头调用：

```ts
// 飞书直连：open.feishu.cn 是国内直连服务，不该跟着走本机代理（HTTP(S)_PROXY 指向的 Clash
// 抖动会让请求挂起——流式卡冻结的根因层）。追加进 NO_PROXY 两种大小写；claude 子进程继承
// 此 env 无害（它们不调飞书；走 Anthropic 的代理策略不受影响）。
export function ensureFeishuDirect(env: NodeJS.ProcessEnv): void {
  for (const key of ['NO_PROXY', 'no_proxy'] as const) {
    const cur = env[key];
    if (cur === undefined || cur.trim() === '') {
      if (key === 'NO_PROXY') env[key] = 'open.feishu.cn';
      continue;
    }
    const items = cur.split(',').map((s) => s.trim());
    if (!items.includes('open.feishu.cn')) env[key] = `${cur},open.feishu.cn`;
  }
}
```

`createFeishuClients` 里、`new lark.Client(...)` 之前加两行：

```ts
  ensureFeishuDirect(process.env);
  // SDK 全局 HTTP 超时：axios 默认 0=永不超时，挂起请求会吊死上层单飞行队列，也让 stop() 的
  // 僵尸帧交接失去 settle 保证。30s 取偏宽（文件上传/下载也走这条实例）。
  lark.defaultHttpInstance.defaults.timeout = 30_000;
```

**禁止**整体替换 `httpInstance`（会丢 SDK 默认实例的 UA 拦截器和 response 解包拦截器，全部调用会坏）。
`defaultHttpInstance` 是 SDK 的具名导出，`lark.defaultHttpInstance` 可直接访问。

### 3.2 `src/feishu/stream-card.ts`（核心）

新增常量（放在既有常量后）：

```ts
// 冻卡修复：单帧 PATCH 超时（对齐 ai-sentinel update_timeout_seconds=3s）。超时 = 放弃该帧
// ——释放单飞行队列让后续帧继续；被放弃的真实请求（僵尸帧）由 client.ts 的 SDK 全局 30s
// 超时兜底 settle，stop() 靠这一点做交接。两处改动是配套的，不可拆开。
const PATCH_TIMEOUT_MS = 3_000;
// 连续失败熔断：≥3 次（含超时）→ 暂停 30s。暂停期 tick/onText 帧跳过（网络断着白费）；
// onToolUse 帧无视暂停（低频、信息量大、兼当恢复探针——一旦成功立即清零解除暂停）。
const FAIL_PAUSE_AFTER = 3;
const FAIL_PAUSE_MS = 30_000;
```

类改动（参考实现可直接采用，允许格式微调；未提到的字段/方法保持原样）：

```ts
export class StreamingCard {
  // ……既有字段全部保留……
  private consecutiveFailures = 0;
  private pausedUntil = 0;
  // 超时放弃后仍在网络上飞着的真实请求（僵尸帧）。stop() 必须等它们全部 settle 再返回，
  // 让调用方随后发的终态卡是最后一帧——否则迟到的进行中帧会覆盖完成卡且再无人纠正。
  private readonly outstanding = new Set<Promise<unknown>>();

  constructor(
    private sender: Pick<Sender, 'updateCard'>,
    private messageId: string,
    private taskName: string,
    private agentKind: string,
    // 可选：不传则静默（兼容既有测试/构造点渐进接线）。
    private logger?: { warn: (obj: object, msg: string) => void },
  ) { /* 原实现不变 */ }

  onToolUse(name: string): void {
    this.toolCount++;
    this.currentTool = name;
    this.markEvent();
    this.scheduleImmediate(); // 变更点：原为 this.schedule()
  }

  // onText / markEvent 不变

  private tick(): void {
    if (this.stopped) return;
    /* 原 stale 判定逻辑不变 */
    if (Date.now() < this.pausedUntil) return; // 熔断期：心跳帧静默跳过
    this.schedule();
  }

  private schedule(): void {
    if (this.stopped) return;
    if (Date.now() < this.pausedUntil) {
      // 熔断期普通帧不发：置 dirty 即可，暂停到期后的第一个 tick/事件会重新驱动。
      this.dirty = true;
      return;
    }
    /* 其余原实现不变（active→dirty / 地板等待 / trailing） */
  }

  // onToolUse 专用：绕过节流地板 + 无视熔断。工具帧低频且信息量大（N tools 实时性
  // 就是靠它），失败也只计一次失败。
  private scheduleImmediate(): void {
    if (this.stopped) return;
    if (this.trailing) {
      clearTimeout(this.trailing);
      this.trailing = null;
    }
    if (this.active) {
      this.dirty = true;
      return;
    }
    this.active = this.flush(true);
  }

  async stop(): Promise<void> {
    this.stopped = true;
    clearInterval(this.ticker);
    if (this.trailing) {
      clearTimeout(this.trailing);
      this.trailing = null;
    }
    if (this.active) {
      try {
        await this.active;
      } catch {
        /* ignore */
      }
    }
    // 僵尸帧交接：等全部 settle（SDK 全局超时保证有限时间，最坏 ~30s），保证终态卡最后落地。
    if (this.outstanding.size > 0) await Promise.allSettled([...this.outstanding]);
  }

  private async flush(force = false): Promise<void> {
    try {
      if (this.stopped) return;
      if (!force && Date.now() < this.pausedUntil) {
        this.dirty = true;
        return;
      }
      this.dirty = false;
      const card = buildStreamingCard(/* 原参数不变 */);
      const sig = JSON.stringify(card);
      if (sig === this.lastSig) return;
      this.lastSentAt = Date.now();

      const real = this.sender.updateCard(this.messageId, card);
      this.outstanding.add(real);
      real.finally(() => this.outstanding.delete(real)).catch(() => {});

      let timer: ReturnType<typeof setTimeout> | undefined;
      const outcome = await Promise.race([
        real.then((ok) => (ok ? 'ok' : 'error')).catch(() => 'error' as const),
        new Promise<'timeout'>((resolve) => {
          timer = setTimeout(() => resolve('timeout'), PATCH_TIMEOUT_MS);
          timer.unref?.();
        }),
      ]);
      clearTimeout(timer);

      if (outcome === 'ok') {
        this.lastSig = sig;
        this.consecutiveFailures = 0;
        this.pausedUntil = 0;
      } else {
        this.consecutiveFailures += 1;
        if (this.consecutiveFailures >= FAIL_PAUSE_AFTER) {
          this.pausedUntil = Date.now() + FAIL_PAUSE_MS;
        }
        this.logger?.warn(
          { messageId: this.messageId, outcome, consecutiveFailures: this.consecutiveFailures },
          'stream card patch failed',
        );
      }
    } finally {
      this.active = null;
      if (this.dirty && !this.stopped) this.schedule();
    }
  }
}
```

语义要点（写测试前先读懂）：

- **超时 ≠ 取消**：race 输了只是"放弃等待"，真实请求继续飞（僵尸帧），由 `outstanding` 追踪。
  中途僵尸帧与新帧乱序落地的短暂显示错乱可接受（≤5s 内被下一帧纠正）；**终态卡不可接受**，
  所以 `stop()` 必须 allSettled。
- **lastSig 只在成功时更新**：失败/超时帧的内容下一帧还会重发（sig 不同或 dirty 驱动）。
- **熔断只暂停普通帧**：`tick()` 在暂停期直接 return（不置 dirty，防空转）；`schedule()`（onText 路径）
  置 dirty 后 return；`scheduleImmediate()`（onToolUse 路径）无视暂停。任何一帧成功即
  `pausedUntil = 0` 恢复。
- **V3 stale 标注不动**：stale 帧走 tick 路径，熔断期发不出去是预期行为（网络断着，标了也到不了）。

### 4.2 `tests/stream-card.test.ts` 新增用例（沿用现有 fake timers 风格：`vi.useFakeTimers()` +
`advanceTimersByTimeAsync`；fake sender 的 updateCard 返回可手控的 deferred promise）

1. **挂起不再冻卡**：updateCard 返回永不 resolve 的 promise → onText 触发一帧 → 推进 3s →
   再 onText 新内容 → 推进 1s → 断言 updateCard 被调用了第 2 次（队列未被堵死）。
2. **超时计失败并熔断**：连续 3 帧全部超时 → 第 4 次 tick（推进 5s）不再调用 updateCard
   （熔断期心跳静默）。
3. **onToolUse 无视熔断**：接上例，熔断期内 onToolUse → updateCard 被调用（探针帧）。
4. **成功解除熔断**：熔断期内探针帧成功（deferred resolve(true)）→ 之后 onText 正常发帧。
5. **熔断到期自动恢复**：3 连败后推进 30s+5s（一个 tick）→ updateCard 再次被调用。
6. **stop() 等僵尸帧**：一帧超时被放弃（真实 promise 仍 pending）→ 调 stop()（不 await 完）→
   断言 stop 未 resolve；手动 resolve 真实 promise → stop resolve。（用 promise 状态哨兵断言。）
7. **onToolUse 立即帧**：t=0 发一帧成功后，t=100ms 时 onToolUse → updateCard 立即被第 2 次调用
   （不等 900ms 地板）。
8. **回归**：既有全部用例（节流、dedup、stale 标注、心跳）不改动逻辑仍绿；若有用例因
   onToolUse 从节流帧变立即帧而断言失效，按新语义修断言（只许改断言，不许改被测行为）。
